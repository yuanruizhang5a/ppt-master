# 01_方案定位

本方案把第一阶段定位为一个范围可控、可证明、可验收的验证闭环，而不是试图一次性验证整个机密计算内核。我们选择一个具有代表性的安全 Rust 内存页管理模块，通过 Aeneas 把实现语义带入 Rocq，再由机器检查的证明固化安全结论。阶段性交付物包括三部分：边界清晰的 Rust 模块，包含功能模型、不变式、定理和可复现脚本的 Rocq 证明工程，以及记录可信边界、假设、结果和局限的验证报告。这样的切分既保留了与真实实现的联系，也为后续扩展到更多模块和属性建立可复用基线。

---

# 02_验证边界

形式化验证的可信度首先来自边界清晰。纳入验证的是代表性的内存页状态管理模块、明确约束下的安全 Rust 代码，以及页面访问、释放和重新分配三类操作；对应性质包括所有权唯一性、共享有效性和清零复用。与此同时，rustc、Charon、Aeneas 的翻译正确性和 Rocq 内核属于可信基，unsafe、内联汇编、并发、硬件微架构、完整内核与端到端侧信道安全暂不在本阶段覆盖范围内。可信并不等于已经证明，因此工具、逻辑基础和硬件假设都必须在报告中显式记录。最终结论只能表述为：在指定模型、假设和代码范围内，目标模块满足所证明的属性，不能外推为整个机密计算系统绝对安全。

---

# 03_总体技术方案

总体技术方案由实现主线和规约主线组成，并在 Rocq 中汇合。实现主线从目标安全 Rust 模块出发，依次经过 rustc 的 MIR、Charon 的 ULLBC 或 LLBC 表示，以及 Aeneas 的 Coq 后端，得到可证明的 Rocq 功能模型。规约主线从安全需求出发，用 DomainId 和 PageId 标识隔离域与页面，再用 PageState 和 KernelState 描述系统状态，并建立 unique ownership、valid sharing 和 reuse is clean 三个核心不变式。两条主线汇合后，为关键操作定义前置条件和后置条件，进而证明隔离、完整性和防泄露定理，并由 Rocq 完成机器检查，最后形成证明脚本和验证报告。整条链路都保留可信边界：rustc、Charon、Aeneas 的翻译正确性、Rocq 内核以及硬件假设不会被证明结论隐含吞并，而是作为可审计前提单独呈现。

---

# 04_证明闭环

证明闭环围绕三个关键操作展开，并以 valid state 作为共同前提。may access 根据页面所有者、共享集合和域身份判断访问是否被授权，用于证明未授权域不能访问页面；release page 移除旧所有权和共享关系并清零内容，用于证明状态转换保持完整性；reassign page 把页面分配给新域，并要求新域看到的初始内容是零页，用于阻断旧数据跨域残留。形式化结论包括：当 may access 返回真时，对应域必须被授权；当 reassign page 成功时，新状态中的页面内容必须等于零页。每个操作既要满足自身后置条件，也要保持全局状态不变式，从而把隔离、完整性和防泄露连成一个可组合的证明闭环。

---

# 05_路线验收与风险

实施路线分为六个阶段：先锁定环境、工具链和可信边界，再实现 Rust 目标模块；随后通过 Charon 和 Aeneas 自动抽取 Rocq 模型，定义安全规约与核心不变式，完成关键操作定理证明，最后进行验收与归档。首阶段以一个模型、三项操作和两类属性为收敛目标，验收时要求 Rocq 工程能够重新编译并通过全部定理检查，Rust、模型、规约和证明之间具有清晰追踪关系，报告则完整记录工具版本、可信边界、限制和复现方法。主要风险包括工具链不稳定、证明规模膨胀、结论被过度解读以及自动化不足，对应策略是固化版本与最小样例、限定模块与核心不变式、强制声明可信边界，并优先沉淀可复用引理。第一阶段的真正价值，是建立一条可复现、可解释、可扩展的 Rust 到 Rocq 验证路径，而不是宣称全系统已经完成验证。
